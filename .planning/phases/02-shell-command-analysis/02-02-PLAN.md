<objective>
Implement the nested command extraction module and the regex matching engine — the two core analysis components that detect dangerous commands hidden inside shell wrappers, interpreters, and subshells, and match them against safety rules with false-positive reduction.

Purpose: These modules deliver the detection capabilities for SHELL-01 through SHELL-06 and SHELL-08. Without nested extraction, `bash -c "rm -rf /"` goes undetected. Without the matcher, rules exist as data but produce no matches.

Output: `src/pipeline/nested.ts` (nested extraction), `src/pipeline/matcher.ts` (matching engine), tests for both
</objective>

    ```typescript
    import type { ParseEntry } from "./types";

    export interface NestedCommand {
      command: string;
      source: "shell-wrapper" | "subshell" | "interpreter";
    }

    export const SHELL_WRAPPERS = new Set([
      "bash", "sh", "zsh", "dash",
      "/bin/bash", "/bin/sh", "/bin/zsh", "/bin/dash",
      "/usr/bin/bash", "/usr/bin/sh", "/usr/bin/zsh",
    ]);

    export const ENV_COMMAND = new Set(["/usr/bin/env", "env"]);

    export const INTERPRETERS: Record<string, string[]> = {
      "python": ["-c"],
      "python3": ["-c"],
      "node": ["-e", "--eval"],
      "ruby": ["-e"],
      "perl": ["-e"],
    };
    ```

    `extractNestedCommands(tokens: ParseEntry[]): NestedCommand[]` logic:
    - Iterate through string tokens only (skip operator/glob/comment tokens for this analysis)
    - Filter to get only string tokens in order
    - For shell wrappers: detect pattern `[wrapper, "-c", <string>]` — extract the string as a shell-wrapper nested command
    - For `/usr/bin/env` pattern: detect `[env, shell, "-c", <string>]` — env followed by shell name then -c
    - For interpreters: detect `[interpreter, flag, <string>]` where flag is in INTERPRETERS[interpreter] — extract as interpreter nested command
    - Return all found NestedCommand objects

    `extractSubshells(tokens: ParseEntry[]): NestedCommand[]` logic:
    - Scan tokens for pattern: string "$" followed by {op: "("} 
    - When found, collect all tokens until matching {op: ")"} (tracking nesting depth for nested parens)
    - Rebuild the inner tokens into a string using space-join of string tokens
    - Return as subshell nested command
    - Also handle bare `(` without `$` if preceded by nothing (grouped command)

    Per D-25: Maximum recursion depth is 10 (tracked by caller in Plan 03 orchestrator, not inside this module).
    Per D-26: Shell wrappers = bash -c, sh -c, zsh -c, dash -c.
    Per D-27: Interpreter one-liners = python -c, node -e, ruby -e, perl -e — regex rules applied to extracted string (not re-parsed with shell-quote).
    Per D-28: Depth tracking done by caller; this module just extracts one level.

    **Step 2: Create src/pipeline/matcher.ts** implementing:

    ```typescript
    import type { Rule, RuleMatch, RuleFilter } from "../types/rule";
    import type { CompiledRule, TokenSpan } from "./types";
    ```

    `compileRules(rules: Rule[]): CompiledRule[]`:
    - Map each rule to `{ rule, regex: new RegExp(rule.pattern, "i") }`
    - Filter to only rules where `rule.category === "shell"` (content rules handled by Phase 5)
    - Per D-43: This is called once at module load time, not per invocation.

    `applyFilters(rule: Rule, segmentStr: string): boolean`:
    - If rule.filters is undefined/empty, return true (match stands)
    - For each filter:
      - "notContains": if segmentStr.includes(filter.value) → return false (reject match)
      - "contains": if !segmentStr.includes(filter.value) → return false (required content missing)
    - Return true if all filters pass
    - Per D-36: Filters serve as post-match guards.

    `matchRules(segmentStr: string, spans: TokenSpan[], compiledRules: CompiledRule[], isShellWrapperArg?: boolean): RuleMatch[]`:
    - For each compiledRule, test regex against segmentStr
    - If regex matches:
      1. Get match result (match text and index)
      2. Apply filters via applyFilters — skip if false
      3. Token position verification (per D-39):
         - Find which TokenSpan the match.index falls into
         - If the span is position "argument" AND isMultiWord is true AND isShellWrapperArg is NOT true → suppress match (return no match for this rule)
         - This implements D-33 (token position filtering) and D-34 (quoted args not analyzed)
      4. If all checks pass, push RuleMatch { rule, matchedText, index }
    - Return collected RuleMatch[]
    - Per D-40: Multiple rules can match; all matches collected.

    **Module-level pre-compilation:**

    import { ALL_RULES } from "../rules/index";

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| segment string -> matcher regex | Untrusted input tested against regex patterns — potential ReDoS |
| nested extraction -> recursion | Deeply nested commands could exhaust resources without depth limit |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | D (Denial of Service) | matcher.ts regex matching | mitigate | Patterns are pre-defined with bounded complexity; no user-supplied regex in hot path; all built-in patterns are non-catastrophic backtracking verified |
| T-02-04 | D (Denial of Service) | nested.ts recursion depth | mitigate | MAX_DEPTH=10 hard limit; stack-based iteration in orchestrator prevents actual call stack overflow |
| T-02-05 | S (Spoofing) | nested.ts shell wrapper detection | accept | Attacker could use unusual shell path (/opt/custom/bash); acceptable because we're protecting against AI agent mistakes, not adversarial humans |
</threat_model>
